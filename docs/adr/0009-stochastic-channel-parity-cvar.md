# M4 stochastic model requires deterministic channel parity and CVaR objective

## Status

accepted

## Context

M4 is not a UI/reporting layer and not a simplified diagnostic. It is the stochastic optimization engine for the final accelerated growth plan. The deterministic PCA model now supports three commercial strategies: salesforce, advertising, and third-party commission. The stochastic model must optimize the same business problem under uncertainty; otherwise the stochastic output is not methodologically comparable with the deterministic PCA.

ADR 0004 selected a two-stage stochastic extension with expected NPV as the first objective. This ADR refines ADR 0004: the target M4 objective is the conservative downside objective `CVaR_5%(VAN)`, with optional expected-VAN tie-break only if needed.

## Decision

M4 will be a sample-average-approximation two-stage stochastic MILP with deterministic channel parity, Latin Hypercube Sampling (LHS), scenario-dependent realized acquisition, fixed investment ticket `VC`, and CVaR valuation objective. `VC` does not vary by scenario; funding stress is reported through liquidity/funding-gap metrics, not by changing the invested capital in VAN.

### 1. Scenario-dependent clients are mandatory

Commercial efficiency multipliers directly alter realized acquisition by scenario:

```text
A_sf[s,t,w] = salesforce_eff[w] * A_sf_plan[s,t]
A_ad[s,t,w] = advertising_eff[w] * A_ad_plan[s,t]
A_tp[s,t,w] = third_party_eff[w] * A_tp_plan[s,t]
A[s,t,w] = A_sf[s,t,w] + A_ad[s,t,w] + A_tp[s,t,w]
```

Therefore active clients must be scenario-indexed and computed dynamically:

```text
C[s,t,w] = sum_c phi[s,c,t,w] * A[s,c,w]
```

It is prohibited to assume fixed traction or fixed active clients in M4.

### 2. Same three acquisition channels as deterministic model

M4 first-stage strategy includes planned channel acquisition, staffing, and advertising investment from month 13 onward. Months 1-12 remain the fixed consensuated acquisition period from `A_base` and are not perturbed by channel-efficiency scenarios. A future extension may require first-year acquisition by channel, but current implementation avoids adding that user input until the UI/input workflow is redesigned.

This is deliberate: before uncertainty is realized, the company commits a commercial plan, not the realized channel efficiency. The stochastic optimizer chooses the plan that performs best under the distribution of unknown efficiencies.

```text
V[t]                  # salespeople
L[t]                  # leaders
I_ad[t]               # advertising investment
A_sf_plan[s,t]        # planned salesforce acquisition
A_ad_plan[s,t]        # planned advertising acquisition
A_tp_plan[s,t]        # planned third-party acquisition
```

Scenario outcomes include realized acquisition by channel, active clients, recurring sales, revenue, operational cost, CAC components, EBITDA, cash, FCF, VAN, breakeven, runway, funding gap, and unit economics. Operational capacity steps `m_op[s,t,w]` remain integer in canonical M4 to preserve deterministic model parity and ADR 0001 operational-cost floor semantics. Commercial recourse is explicitly out of scope for current implementation: scenarios do not increase sellers, leaders, advertising investment, or third-party planned acquisition after efficiency is observed. This may be added later as bounded commercial recourse.

Advertising must preserve the deterministic continuous response semantics from ADR 0006:

```text
sum_s A_ad_plan[s,t] = a + b * I_ad[t]
I_min <= I_ad[t] <= I_max
sum_s A_ad_plan[s,t] <= A_ad_cap
```

Third-party commission is modeled as a percentage of revenue generated by third-party-origin service cohorts for `commission_periods` months, including initial and recurring revenue inside the window. This is a channel cost over attributable third-party revenue only, never a company-wide revenue share. A future extension may support one-time initial-sale-only commissions as an alternate policy, but it is out of scope for current implementation.

Channel share constraints apply to the ex-ante plan, not the realized scenario quantities:

```text
A_channel_plan_total[t] >= min_share * A_plan_total[t]
A_channel_plan_total[t] <= max_share * A_plan_total[t]
```

### 3. Backend-static stochastic configuration

The `stochastic` configuration block is an internal system configuration for M4 orchestration. It must not be exposed as editable fields in the user-facing UI form. This preserves consistency across pipeline iterations.

M4 defaults live in code or internal config, not in the startup input form. User-facing YAML should describe the startup/business case; M4 sampling policy, CVaR alpha, scenario counts, and distribution parameters are controlled by backend defaults unless an engineer explicitly changes them.

The same rule applies to M4-only extensions of third-party behavior, including default `commission_periods`, if not already part of the user-facing deterministic business schema.

### 4. Probability distributions for LHS

LHS uses bounded triangular distributions with inverse-CDF sampling implemented natively, without scipy or other heavy dependencies.

Default distributions:

| Variable | Triangular distribution | Interpretation |
|---|---:|---|
| churn multiplier | min `0.8`, mode `1.0`, max `1.3` | stress can raise churn up to +30% |
| salesforce efficiency | min `0.5` to `0.7`, mode `1.0`, max `1.2` to `1.3` | saturation/downside can reduce conversion materially |
| advertising efficiency | min `0.5` to `0.7`, mode `1.0`, max `1.2` to `1.3` | media efficiency uncertainty |
| third-party efficiency | min `0.5` to `0.7`, mode `1.0`, max `1.2` to `1.3` | partner throughput uncertainty |
| WACC multiplier | min `0.7`, mode `1.0`, max `1.5` | downside includes inflation/country-risk rate stress |

`VC` is fixed across scenarios. The former prototype's financing multiplier is not part of canonical M4 because it mixes operating uncertainty with the size of the committed investment ticket.

Exact efficiency minima/maxima are backend defaults and must be stable across UI runs. Initial recommended defaults are:

```text
salesforce_efficiency:  triangular(0.6, 1.0, 1.2)
advertising_efficiency: triangular(0.5, 1.0, 1.3)
third_party_efficiency: triangular(0.7, 1.0, 1.2)
churn_multiplier:       triangular(0.8, 1.0, 1.3)
wacc_multiplier:        triangular(0.7, 1.0, 1.5)
```

### 5. Conservative CVaR objective

M4 objective is conservative downside value over a linear VAN expression. Terminal value inside the MILP uses a linear continuation proxy:

```text
terminal_value[w] = discount[H,w] * terminal_multiple * 12 * EBITDA[H,w]
```

No `max(EBITDA, 0)`, binary truncation, or nonlinear terminal-value policy is allowed inside the optimization. If the final EBITDA is negative, Due Diligence should normally catch the case before M4; post-processing/reporting may separately show a normalized DCF terminal-value policy for interpretation, but it does not change the M4 objective.

```text
max CVaR_alpha(VAN), alpha = 0.05
```

Linear formulation:

```text
z[w] >= eta - VAN[w]
z[w] >= 0
CVaR = eta - (1 / alpha) * sum_w p[w] * z[w]
maximize CVaR
```

A tiny expected-VAN tie-break may be added only to break degeneracy:

```text
maximize CVaR + epsilon * E[VAN]
```

### 6. Post-SAA Monte Carlo evaluation

After solving SAA, the first-stage strategy is fixed and evaluated over a larger out-of-sample LHS sample. This evaluation does not reoptimize. It produces the probability distribution of valuation and operating outcomes. Both SAA (`N=100`) and ex-post evaluation (`N=1000` by default) use LHS for variance reduction and stable tail metrics.

Required metrics include:

- expected VAN, p5/p10/p50/p90 VAN, CVaR_5, P(VAN < 0)
- final active clients p10/p50/p90 and milestone hit probabilities, where milestones are evaluated on `final_active_clients = sum_s C[s,H,w]`, not gross cumulative acquisition
- breakeven-month distribution and P(no breakeven)
- runway distribution and P(cash below liquidity floor), where runway is the first month `Caja[t,w] < floor[w]`; current default floor is ticket-indexed `-VC[w]`, with no nonlinear logic added
- expected and maximum funding gap
- CAC, LTV/CAC, ARPU, ARR distributions

## Consequences

- Existing `stochastic/model.py` is no longer sufficient because it lacks channel parity and CVaR valuation objective.
- M4 implementation must be updated before claiming a final stochastic PCA.
- UI should not expose stochastic distribution controls; it should only trigger M4 and display artifacts/status.
- Stochastic outputs are first-class valuation artifacts, not legacy report decorations.
